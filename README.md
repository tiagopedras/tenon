# Tenon

The shared design system for the projects in `~/Code`. Code is the source of
truth; the Figma library is a replica built from it, not the other way round.

Today Tenon is tokens and nothing else. That is deliberate. A component built
on a token set that is still moving has to be rebuilt when the set settles, so
the tokens hold still first and React components come after.

## Where it came from

The to-dos board is the furthest-along project here, and its `board.css`
already carries a two-tier token block: primitives that are ramps with no
opinion, semantics that say what a colour is *for*. Tenon keeps that shape and
takes its colour anchors from it, so the board's palette survives the move.

The other parent is the Twinkl design system, read from the snapshot at
`ds-inventory/snapshots/figma/2026-09-04`. Tenon copies its structure —
nineteen-step ramps numbered 50 to 950, spacing numbered so that 100 is 8px, a
semantic colour layer split into background, text, icon and stroke — and none
of its values.

Two things Twinkl does that Tenon does not. It has 102 component tokens, almost
all of them for the button, and Tenon has none: a component's CSS reads
`var(--tenon-background-accent)` directly, and a component needing a value no
semantic token covers means the semantic layer has a gap to fill rather than a
component token to add. And its semantic colour layer carries fourteen loose
tokens at the top level (`accent`, `border`, `foreground`) that duplicate what
is in the four groups below them. Tenon has the four groups only.

## The two tiers, and what is not in them

Colour and typography have two tiers. Everything else has one.

A semantic tier exists so a value can change between themes while the name
stays put. That is the whole job. A gap of 8px is 8px in dark mode, so
`space/gap/default → spacing/200` would be a rename with a lookup hop attached.
So spacing, radius, border width, breakpoints and icon sizes all read one
`dimension` scale directly, and the rule that nothing reads a primitive applies
to colour, where it earns its keep.

Twinkl is inconsistent in both directions here — its spacing sits in primitives
with nothing above it, its rounding sits in semantics with nothing below it —
and Tenon collapses both onto the single scale. Radius keeps names (`radius.md`,
`radius.full`) because a radius is the one measurement a component should not
pick freely, but those names alias the same scale everything else reads.

If a compact or scaled density ever arrives, the dimension scale itself becomes
mode-aware. Every `var()` call site stays exactly as it is.

## Colour

Seventeen hues by nineteen steps, plus four values that sit outside the ramps.
Every one of the 327 is generated by `scripts/generate-ramps.mjs` from a single
anchor hex, in OKLCh, so that blue-600 and green-600 are the same weight on the
page. Eleven of the anchors are colours the board already used; five fill gaps
in the wheel so there is a distinct hue available per bucket as the board grows.

The generated ramps are consistent enough to state a rule: **every hue clears
4.5:1 against white by step 550 or 600, and against a dark panel by step 450 or
500.** Picking a colour for text is now a lookup rather than a measurement.

`base.white` and `base.black` are endpoints rather than steps, and keeping them
off the neutral ramp is what stops "the lightest neutral" quietly becoming pure
white. `base.urgent` and `base.soon` are the timeline's overdue and due-soon
fills, at full chroma on purpose: the board found that a red at the same
saturation as the categorical hues read as an eleventh bucket rather than as a
warning.

The ten categorical `chart.1`–`chart.10` tokens are one step off ten different
ramps. They do the job the board's bucket colours do.

## Typography

A size ramp from 10px to 71px. Below `xl` those are the sizes the board already
uses, rounded off the half-pixels it had drifted into; above it the ratio is
1.2, which is the range a page that is not the board will want.

Six headings, `heading-1` through `heading-6`, plus body, body-sm, label,
caption and code. They land at the small end of the ramp because the board is a
dense UI: `heading-1` is 19px, not 49px. When Tenon goes into a project with
room to breathe, the headings move up the ramp and nothing else changes.

Weights collapse from the board's thirteen — which included 520, 560, 570 and
680, the kind of value that gets typed once and copied forever — to four.

One Figma constraint worth knowing before the library gets built. Figma
variables cannot hold a composite value, so the six headings land there as
**text styles** and the three elevations as **effect styles**. Only the parts
(size, weight, line height, letter spacing) can be variables. The code side
stays one file either way.

## The build, and the check that is the point of it

```bash
npm run all        # regenerate the ramps, then build
npm run build      # build only
npm run check      # build quietly, for a pre-commit hook
```

`scripts/build.mjs` writes `dist/tenon.css` and `dist/tenon.tokens.json`, and
refuses to write either if any of three checks fail: light and dark must hold
the identical key set, every `{alias}` must resolve, and no semantic token may
alias another semantic token.

The first is the reason a token pipeline exists here at all. `board.css` had
`--accent` missing from its dark block for months, used as a `color:` in
twenty-two places and as a border in nine more, and nothing said a word,
because a hand-written stylesheet has no way to know a key is absent. A fourth
check reports WCAG contrast for every text and icon token against its own
background, and reports rather than fails, because `text.faint` is meant to sit
where it sits.

## Using it

```css
@import "@tiagopedras/tenon/tenon.css";
```

`:root` carries light. Dark applies when the system asks for it, unless
`[data-theme="light"]` is set, and applies unconditionally under
`[data-theme="dark"]`. A manual toggle needs no rebuild.

```css
.card {
  background: var(--tenon-background-raised);
  border: 1px solid var(--tenon-stroke-default);
  border-radius: var(--tenon-radius-lg);
  padding: var(--tenon-dimension-200);
  box-shadow: var(--tenon-elevation-raised);
}
```

Text styles come as five variables each and as a class:

```html
<h2 class="tenon-heading-2">Design oversight</h2>
```

## What changes cheaply and what does not

Adding a hue, a step, a semantic token or a theme is an edit and a rebuild.
Changing an anchor hex moves all nineteen of that hue's steps at once, which is
visible but contained.

Renaming a semantic token after an app consumes it breaks every `var()` that
reads it. So the semantic names are worth arguing about now, and the primitives
are disposable: nothing outside `dist/tenon.css` should ever name one.
